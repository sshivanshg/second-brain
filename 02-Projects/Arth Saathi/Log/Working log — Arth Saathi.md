- **Cut mobile sync cost without touching the local-first architecture — manifest-gated fast path + full-sweep backstop.** Founder flagged that "syncing the mobile app with the DB feels cost-inefficient and bad for the DB," with the instinct that we're hoarding invoices on-device and should maybe stop syncing. Split the bundled worry before acting: (1) **device storage is a non-issue** — a shop's khata/invoices are a few MB of text, and **binary files (receipt photos, invoice PDFs, selfies) are never in SQLite or the sync payloads** — they live in S3/R2 and travel as URL strings; (2) the real cost was **empty-sync frequency**, not data volume — `syncAll()` fired on *every* foreground/boot and pulled **all 8 entities even when nothing changed** (open the app 30×/day → ~240 near-empty round trips/device/day). Also called out the trap: going **online-only would *increase* DB load** (every screen read hits Postgres, no local cache) and break offline, which is the whole point for a patchy-connectivity Bharat user. **Fix (frequency, not architecture):** new `GET /mobile/sync/manifest` returns `MAX(updatedAt)` per entity as an **index-tip, tenant-scoped read**; the mobile fast path (foreground/boot/auth) is now **throttled to ≤1/60s** and hits the probe first, **pulling only the entities whose max moved past the local cursor** — nothing-changed case drops from **8 full pulls → 1 cheap probe + 0 pulls**. Kept the probe cheap by *excluding* low-churn reference tables that lack a `(businessId, updatedAt)` index (categories/instruments/line-items); the **hourly background full sweep** (ignores the manifest) is the correctness backstop that catches those within the hour — which **avoids a prod index migration for an unmeasured cost**. Added **instrumentation** (Sentry breadcrumb + `lastRun` in the sync store) so the bill becomes *measured* before deciding the bigger follow-ups (multiplex pull, retention window, pooling). Backend + mobile `tsc` 0 new errors; manifest service has a gated integration test (empty-tenant, change-detection, multi-table GREATEST, cross-tenant isolation). Repo doc `docs/architecture/mobile-sync-manifest.md` · thinking in [[Mobile sync cost — manifest-gated fast path]]. **Lesson:** a local-first sync that *feels* expensive is usually a **frequency** problem, not a storage or architecture one — measure empty round-trips first; the cheapest win is "ask *whether* to sync before *doing* it."
